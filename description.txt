2. HOW FEATURES ARE IMPLEMENTED
--------------------------------

AUTHENTICATION:
- Registration: POST /api/auth/register with username/email/password/phone. Backend hashes password with BCrypt, saves user with role USER, returns JWT.
- Login: POST /api/auth/login. Validates credentials, returns JWT.
- JWT flow: Frontend stores token in localStorage (urbannest-token). Axios interceptor attaches "Authorization: Bearer <token>" to every request. JwtAuthenticationFilter on backend validates token on every request, loads User from DB, sets Spring Security context.
- Auto-login: On app mount, AuthContext checks if token exists in localStorage, calls GET /api/auth/me to validate it. If invalid, clears token.
- Logout: Clears token + user from localStorage, sets user state to null.
- 401 handling: Axios response interceptor catches 401 responses, clears token, redirects to /login.

PROPERTY LISTING (PUBLIC):
- Home page fetches approved properties via GET /api/properties with optional query params (keyword, type, status, location, minPrice, maxPrice, sort, dir).
- Backend PropertyService.search() builds JPA Specifications dynamically. Always filters by approvalStatus=APPROVED. Only APPROVED properties are visible to the public.
- Property cards show image (with placeholder fallback), title, type badge, location, beds/baths/sqft, price, and a favorite heart button.

PROPERTY CREATION (LOGGED-IN USERS):
- Multi-step form: Step 1 (title, listing type, property type, price, township from predefined list), Step 2 (bedrooms, bathrooms, sqft), Step 3 (description), Step 4 (image URL).
- POST /api/properties creates property with approvalStatus=PENDING. Not visible on public listing until admin approves.
- PUT /api/properties/{id} updates property (owner only). Resets approvalStatus to PENDING.

PROPERTY APPROVAL (ADMIN):
- AdminDashboard shows pending properties (GET /api/admin/properties?approvalStatus=PENDING).
- Admin can approve (PUT /api/admin/properties/{id}/approve) or reject (PUT /api/admin/properties/{id}/reject).
- AdminDataManagement shows all properties with ability to view or delete.

FAVORITES:
- Logged-in users can favorite/unfavorite properties via POST/DELETE /api/properties/{id}/favorite.
- Backend uses a Favorite entity (unique constraint on user_id + property_id) to prevent duplicates.
- Dashboard shows user's favorites (GET /api/favorites).
- Home page PropertyCard initializes heart state from fetched favorites list.

USER MANAGEMENT (ADMIN):
- AdminDashboard shows total users, pending approvals.
- AdminDataManagement shows user table with role toggle (ADMIN <-> USER) and delete.
- Admin can update any user's role or delete any user (cascades to their properties and favorites).

PROFILE MANAGEMENT:
- Dashboard "Profile & Security" tab allows updating email/phone (PUT /api/users/me) and changing password (PUT /api/users/me/password).

3. FRONTEND/BACKEND CONNECTION
-------------------------------

- Frontend runs on http://localhost:5173 (Vite dev server)
- Backend runs on http://localhost:8080 (Spring Boot + Tomcat)
- Frontend connects directly to backend via Axios with baseURL "http://localhost:8080"
- CORS is configured in SecurityConfig.java to allow http://localhost:5173
- API endpoints used by frontend:
  * authAPI: POST /api/auth/register, POST /api/auth/login, GET /api/auth/me
  * userAPI: PUT /api/users/me, PUT /api/users/me/password, GET /api/users, PUT /api/users/{id}, DELETE /api/users/{id}
  * propertyAPI: GET /api/properties, GET /api/properties/mine, POST /api/properties, GET /api/properties/{id}, PUT /api/properties/{id}, DELETE /api/properties/{id}, GET /api/favorites, POST /api/properties/{id}/favorite, DELETE /api/properties/{id}/favorite
  * adminAPI: GET /api/admin/properties, PUT /api/admin/properties/{id}/approve, PUT /api/admin/properties/{id}/reject, PUT /api/admin/properties/{id}, DELETE /api/admin/properties/{id}

4. SECURITY CONFIGURATION
--------------------------

URL-level rules (SecurityConfig.java):
- POST /api/auth/register, POST /api/auth/login -> permitAll (public)
- GET /api/auth/me -> authenticated
- PUT /api/users/me, PUT /api/users/me/password -> authenticated
- GET /api/users, PUT /api/users/*, DELETE /api/users/* -> hasRole('ADMIN')
- GET /api/properties/mine, POST /api/properties, PUT /api/properties/*, DELETE /api/properties/* -> authenticated
- GET /api/properties, GET /api/properties/* -> permitAll (public read)
- /api/favorites, /api/favorites/** -> authenticated
- POST/DELETE /api/properties/*/favorite -> authenticated
- /api/admin/** -> hasRole('ADMIN')
- Everything else -> authenticated

Method-level security: @EnableMethodSecurity is enabled. Some controllers also use @PreAuthorize("hasRole('ADMIN')") as defense-in-depth.

5. DATABASE
------------

- PostgreSQL on localhost:5432, database "realestate", user "postgres"
- Tables: users, properties, favorites
- Properties.owner is a foreign key to users.id (required, LAZY fetch)
- Favorites has a unique constraint on (user_id, property_id)
- DataSeeder creates admin (admin/admin12345) and demo (demo/demo12345) on first run when users table is empty.

6. REMAINING ERRORS / ISSUES
------------------------------

A. AddEditProperty multi-step form doesn't validate per step (UX issue):
   - File: frontend/src/pages/AddEditProperty.tsx
   - The "Next" button is type="button" so it skips HTML5 required validation.
   - Users can click through all 4 steps with empty fields. Validation only fires on final submit (step 4), but the user can't see which fields on earlier steps are missing.
   - Fix: Add a validateStep(currentStep) function in handleNext that checks current step's required fields before advancing.

B. LanguageContext has dead code:
   - File: frontend/src/contexts/LanguageContext.tsx
   - The t() function, translations object, and LanguageContext interface still exist but language is hardcoded to 'en'.
   - setLanguage and toggleLanguage are no-ops.
   - Either remove the entire language system or re-enable language switching.

C. Home.tsx still has Myanmar text in FEATURES array (lines 11-15):
   - titleMy and descMy fields exist in the FEATURES objects but are never used since language is always 'en'.
   - Minor dead code, harmless.

D. No pagination anywhere:
   - Backend returns all records for properties, users, favorites.
   - Would be slow with large datasets but fine for a school project.

E. N+1 query pattern:
   - PropertyService.toResponse() accesses property.getOwner() which triggers lazy loading.
   - When called in loops (search results, favorites list), this causes separate DB queries for each property's owner.
   - Fix would require @EntityGraph or JOIN FETCH queries in repositories.

F. Admin can delete themselves or the last admin:
   - File: backend/src/main/java/com/urbannest/backend/service/UserService.java
   - No guard preventing an admin from deleting their own account or the last admin account.

G. AdminDashboard pending property images use raw <img> via PropertyImage component:
   - Already fixed to use PropertyImage with placeholder fallback.
   - But the AdminDataManagement page still uses raw <img> with onError hide for property images in the table (lines 216).
   - Minor visual glitch if image URL is broken.

H. Some CSS classes defined in index.css (auth-page, auth-signin, auth-left, etc.) are not used by the current LoginRegister.tsx component which uses Tailwind classes directly.
   - Dead CSS, harmless but could be cleaned up.

I. The Favorites feature on Dashboard calls propertyAPI.getFavorites() which returns PropertyResponse objects (not Favorite objects). This means we lose the favorite ID and can't distinguish between "property ID" and "favorite ID" if they ever differ. Currently fine since favorite.id != property.id but the code uses property.id for removal which is correct.

J. Navbar mobile menu doesn't show an Admin link for admin users.
   - File: frontend/src/components/Navbar.tsx
   - Desktop navbar shows "Admin" button for ADMIN role, but the mobile dropdown (lines 47-55) only has Dashboard and Favorites links.
